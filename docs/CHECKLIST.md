# COMPASS-HYBRID: проблемы и чек-лист доработок

Кейс-чемпионат «Клинический компас 2026». Актуально на 17.10.2026.
Источники: документация проекта (`Документация_проекта.docx`) и текст кейса (`Кейс_цифровой_помощник_клинический_компас.pdf`).

**Приоритеты:** `P0`: теряем баллы по обязательным условиям или есть риск безопасности/закона. `P1`: проседает отдельная метрика или задача. `P2`: полировка.

**Что я не мог проверить сам** и помечаю `ПРОВЕРИТЬ`: детали ОХЛП, регистрацию препаратов, условия лицензий шкал, статус КР. Всё это сверять по первоисточникам (ГРЛС, рубрикатор КР, правообладатели шкал).

## 0. Решения, которые надо принять первыми

- [ ] **Канал пациента: PWA на своём домене вместо мессенджера.**
  - Любой мессенджер — третья сторона в канале (Условие 2 «без участия третьих лиц»).
  - MAX: публикация ботов и мини-приложений идёт только через верифицированные юрлица РФ, ИП/самозанятые/физлица не допускаются (источник: https://habr.com/en/articles/951326). У команды юрлица скорее всего нет.
  - Telegram Mini App — та же веб-страница в webview, PWA ничего не теряет.
  - Реализация: ссылка/QR от врача → сайт → «установить на экран». Для iOS push работает только у установленного PWA (iOS 16.4+), нужен онбординг-экран.
- [ ] **Каналы алерта врачу: WebSocket + Web Push + резерв (email/SMS через российский шлюз, на демо эмулировать).** Во всех каналах только пустой пинг «откройте систему», без клинического текста. Неподтверждённые алерты хранятся в БД и висят красным баннером при входе.
- [ ] **Правила «Авиандра»: либо универсальный вычислитель правил по данным, либо Python-движок.** C-ядро с зашитыми правилами ломает метрику 10 (см. п. 3.10).
- [ ] **Нейросети (RouterNet, DissimulationDropoutNet, ClusterVerifyNet): убрать или явно пометить «прототип на синтетике, не влияет на рекомендации».** Они ломают метрику 5 и не имеют данных обучения.
- [ ] **Фичи на вырез** (нет обоснования, дают атаку жюри без выигрыша): генотипы LCT/SLC6A4/HTR2A как основание выбора препарата, Pharmacophobia_Nocebo_Score, Circadian_Alignment_Index, rPPG + индекс Баевского (обычно считается по ~5-минутной записи, 30 секунд не хватит), «Авиандр как кардиобезопасная альтернатива при QTc > 450», 24-мерный вектор z_t целиком.
- [ ] **Голосовой модуль: решить, что это.** Kintsugi DAM построена на `whisper-small.en` (английская речь), на русском не валидирована. Либо показывать как «демо-прототип, вне клинического контура», либо убрать из рекомендаций и алертов. Проверить лицензию и ограничения в model card.

## 1. Обязательные условия кейса

### 1.1 Условие 2: связь врач-пациент «без участия третьих лиц» `P0`
**Проблема:** план гонит данные и алерты через Telegram.
- [ ] Убрать клинический контент из любых сторонних каналов (см. п. 0).
- [ ] Привязка пациента к врачу: одноразовый QR-токен с TTL, после использования инвалидируется.
- [ ] Показать на демо путь данных: пациент → ваш сервер → карточка врача, без посредников.

**Готово когда:** схема потока данных на слайде, ни один клинический байт не уходит за пределы вашего контура.

### 1.2 Условие 3: решение не выполняет клинических действий само `P0`
**Проблема:** в документе система самостоятельно делает следующее.
- «успокаивает пациента, бросать приём не нужно» при головокружении (это решение о продолжении терапии);
- шлёт автоматический КПТ-инструктаж;
- сама отвечает пациенту по режиму приёма;
- предлагает вызов психбригады по ст. 29 (решает психиатр);
- hard stop физически блокирует врача без override.

- [ ] Заменить «успокаивает/не бросайте» на цитату из ОХЛП («обычно проходит самостоятельно») + «сообщите врачу» + автоматическая запись в карточку врача.
- [ ] Все тексты, которые видит пациент, заранее утверждает клиницист (список текстов, подпись/дата).
- [ ] Убрать из алерта автоматическую «дифференциацию по ст. 29». Оставить: уведомление врача, кризисные контакты пациенту, черновик направления на подтверждение.
- [ ] Hard stop заменить на «жёсткое предупреждение + override с обязательной причиной и записью в аудит». Off-label только по решению врача/ВК.
- [ ] Все изменения терапии, направления и планов: кнопка подтверждения врачом + запись `confirmed_by`, `confirmed_at`.

**Готово когда:** по каждому исходящему действию системы можно ответить «кто подтвердил».

### 1.3 Условие 4: сценарии «профиль + рекомендации + маршрутизация» `P0`
- [ ] **Сценарий 3** сейчас склеен из двух разных пациентов (А и Б). Переписать как одного пациента со всеми тремя частями.
- [ ] Для пациента с противопоказанием: что система рекомендует вместо «Авиандра» (in-label альтернатива) и её собственные противопоказания.
- [ ] **Сценарий 2**: убрать «генотип CYP2D6 в ЭМК» как исходный факт (нереалистично для амбулатории) или явно пометить как «результат внешнего теста, внесённый врачом».
- [ ] Каждый сценарий: профиль, шкалы с баллами, рекомендация со ссылкой на пункт ОХЛП/КР, маршрут (зелёный/янтарный/красный).

### 1.4 Условие 5/6: алертинг и визуальное выделение `P0`
- [ ] Определить цепочку эскалации: подтверждение врачом в N минут → если нет, второй врач/резервный канал.
- [ ] Метрика доставки: «время до подтверждения человеком», а не «45 мс».
- [ ] Сообщение пациенту не обещает срок реакции и не говорит «врач уже оповещён», если нельзя гарантировать мониторинг. Добавить: «это не экстренная служба, при угрозе жизни звоните 112».
- [ ] Красный и янтарный блоки различимы по форме и иконке, а не только по цвету (проверить в режиме ч/б).

### 1.5 Условие 7: только ЛП в рамках инструкции `P0`
- [ ] Плашка про паническое расстройство и РДР для «Авиандра» остаётся справочной и не попадает в карточку вариантов терапии.
- [ ] Проверить таблицу п. 5.1: регистрация и показание «ГТР»/«депрессия» именно в инструкции каждого препарата (КР и инструкция могут расходиться).

### 1.6 Условие 8: валидированные шкалы, источники, лицензии `P0`

### 1.7 Условие 9: законодательство РФ `P0`

## 3. Технические метрики

### 3.1 Быстродействие `P1`
- [ ] Замерять end-to-end по API (запрос врача, формирование рекомендации, доставка алерта), а не время C-функции.
- [ ] Записать медиану и p95 для каждого узла, указать железо.

### 3.2 Обработка историй болезни разных шаблонов `P0/P1`
- [ ] Утверждение «Outlines = без галлюцинаций» убрать: Outlines гарантирует структуру JSON, а не истинность значений.
- [ ] Для каждой извлечённой сущности требовать текстовый фрагмент-источник (evidence span) и отбрасывать значения без него.
- [ ] Основной путь детерминированный (правила/словари), LLM только как резерв. Qwen2.5-1.5B на русском клиническом тексте слаб.
- [ ] Тест на чужих шаблонах: хотя бы 20 историй, написанных другим человеком или другой моделью в другом стиле. Жюри почти наверняка даст свои шаблоны.
- [ ] Отдельные тесты: отрицания («эпилепсии нет»), даты («СКФ 52 в 2019 г.»), единицы (мкмоль/л и мг/дл), сокращения.
- [ ] Корпус и словарь сокращений делает разный человек (иначе утечка и тавтология метрики).

### 3.3 Надёжность и корректность `P0`
- [ ] Ввести tri-state для флагов (да/нет/неизвестно) и NaN для чисел. Сейчас `uint8 0/1` превращает пропуск в «нет».
- [ ] «Unknown» не может давать зелёный In-Label (всегда янтарное «нужны данные»).
- [ ] Добавить в структуру асцит и энцефалопатию (без них Чайлд-Пью не считается). `days_since_maoi`: отдельное значение «никогда» (не sentinel 255).
- [ ] `ПРОВЕРИТЬ` в ОХЛП: критерий «СКФ» или «КК» (Кокрофт–Голт). Реализовать оба, брать консервативный.
- [ ] Тест-набор граничных значений (СКФ 59/60/61, Чайлд-Пью, ИМАО 13/14/15 дней).

### 3.4 Эргономика `P2`
- [ ] Хронометраж «с системой / без» на реальных кликах, количество действий считать автоматически (лог событий).

### 3.5 Обоснованность выводов `P0`
- [ ] Для каждой рекомендации и предупреждения: цепочка `rule_id → пункт ОХЛП/КР → входные значения`, видимая врачу по клику.
- [ ] Таблица `guideline_sources` с версиями и датами (см. п. 3.12).
- [ ] SHAP убрать (нейросети вне контура рекомендаций).

### 3.6 Устойчивость к нагрузкам `P1`
- [ ] Нагрузочный тест по API (Locust/k6), заявить фактические: число одновременных пользователей, p50/p95 при 10/100/1000.
- [ ] Redis `appendfsync always` ограничивает пропускную способность, учесть в замере.

### 3.7 Отказоустойчивость и восстановление `P0/P1`
- [ ] Источник истины Postgres, Redis только транспорт (transactional outbox).
- [ ] «RPO = 0» несовместим с асинхронной репликацией. Либо синхронная репликация с замером задержки, либо заявить реальное значение.
- [ ] Реальный restore-drill: бэкап → уничтожение → восстановление, зафиксировать время (RTO) и потерянные записи (RPO).
- [ ] Критический пакет в сбой: клиент хранит в IndexedDB, сервер идемпотентно принимает по `event_uuid`, врач видит алерт при следующем входе даже если был оффлайн.
- [ ] iOS Safari: Background Sync недоступен, досылка идёт при открытии приложения. Заявить честно. Кризисный экран пациенту показывается локально без сервера.

### 3.8 Кроссплатформенность `P1`
- [ ] Тест-матрица: iOS Safari (PWA), Android Chrome, Windows/macOS, Astra Linux или РЕД ОС + Chromium/Яндекс.Браузер. Результат: таблица «работает / ограничения».

### 3.9 Масштабируемость `P2`
- [ ] Две реплики API за nginx + общий Redis/Postgres, замер масштабирования. «Kubernetes-ready» без проверки не писать.

### 3.10 Гибкость архитектуры `P0`
- [ ] Правила «Авиандра» зашиты в `ohpl_hardstops.c`: новый препарат = перекомпиляция. Решить (см. п. 0): данные + универсальный вычислитель.

- [ ] Демо: добавить новую шкалу или новый препарат в JSON и показать, что регрессионные тесты прошли.

### 3.11 Гибкость работы с данными `P2`
- [ ] Показать фильтры/выборки по пациентам, шкалам, периоду, статусу алерта. Индексы и план запроса для 2–3 типовых запросов.

- [ ] `messages` / `message_receipts` (Задача 6);

- [ ] `rule_versions`, `scale_versions` (версионирование);

### 3.13 Защищённость данных `P0`

- [ ] Негативный тест RLS: врач A не видит пациента врача B (скриншот/лог теста).
